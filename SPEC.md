# ARLI Discovery Extension v1.4.0

Лицензия: Apache-2.0 (см. `LICENSE`, `NOTICE`, `TRADEMARK.md`).
Нормативный текст для публикации: `spec/SPEC.en.md` (английский). Этот файл рабочий
перевод, номера пунктов совпадают. Состояние публикации: `spec/PUBLISHING.md`.
Публикация не выполнена.

Расширение к A2A 1.0 для обнаружения независимых агентов по намерению с проверяемым
доказательством. URI расширения: `https://arliwork.com/a2a/extensions/arli.discovery.v1`.

Слова **MUST**, **MUST NOT**, **SHOULD**, **MAY** означают обязательность так, как это
принято в нормативных документах. Реализация, соответствующая этому тексту, получает
ответ «соответствует» от набора проверок (`python -m arli_engine.conformance`).
Если набор расходятся с этим текстом, правым считается набор: он и есть обещание.

Область. Расширение описывает только слой обнаружения: объект намерения, честный перечень
возможностей, согласование ключа, сопоставление, конверт доказательства, грамматику
переговоров и согласие человека. Транспорт, задачи и сообщения берутся из A2A как есть.

## 1. Намерение

1.1. Намерение MUST нести поля: `intent_id`, `owner`, `network`, `type`, `statement`,
`status`, `provenance`.
1.2. `type` MUST быть одним из: `person`, `supply`, `demand`. Намерения типа `supply`
сопоставляются с `demand` по общей теме; два `supply` между собой MUST NOT считаться
совпадением.
1.3. `status` MUST быть одним из: `active`, `paused`, `archived`. Сопоставление
участвует только в `active`.
1.4. `provenance` MUST быть одним из: `human`, `organisation`, `synthetic`. Сеть MUST
объявлять, допускает ли она синтетические намерения; по умолчанию сеть человеческая, то есть
не допускает. В такой сети синтетическое намерение MUST отклоняться с кодом
`synthetic_not_admitted`, а не участвовать в сопоставлении.
1.5. Намерение MUST нести юрисдикцию, правила хранения берутся из неё, а не из места сервера.

## 2. Возможности агента

2.1. Карточка агента MUST отдаваться по стандартному адресу `/.well-known/agent-card.json`
и MUST быть подписана JWS (alg ES256). Защищённый заголовок MUST нести `jwk`, чтобы чужая
сторона могла проверить карточку, не получая ключ по отдельному каналу.
2.2. Подпись MUST ломаться при любой правке тела карточки.
2.3. Каждая операция агента MUST объявлять последствия по всем семи ключам:
`mutates_artifact`, `launches_process`, `may_show_ui`, `may_access_network`,
`may_write_filesystem`, `changes_permissions`, `requires_root`.
2.4. Необъявленный эффект MUST трактоваться как возможный, а не как отсутствующий.
2.5. Недоступная операция MUST оставаться в перечне и MUST нести причину с кодом из
набора: `available`, `unsupported_host`, `missing_dependency`, `not_configured`,
`disabled_by_policy`.
2.6. Перечень MUST отдаваться отдельным документом
`/.well-known/arli-capabilities.json` с признаком `fail_closed`.

## 3. Согласование ключа и отпечатки

3.1. Ключ пары MUST выводиться согласованием ECDH на кривой P-256 и HKDF-SHA256, где во
вход входят оба идентификатора агентов и идентификатор сессии. Ключ пары MUST NOT
передаваться по проводу.
3.2. Отпечаток признака MUST быть привязан к сессии и к канонической метке пары, одинаковой
у обеих сторон. Привязка к стороне отправителя MUST NOT применяться: она ломает сопоставление.
3.3. Каждая сторона MUST NOT отправлять значения признаков; наружу уходят только отпечатки
или ослеплённые значения.
3.4. Один обмен MUST происходить не чаще одного раза на пару и сессию.

## 4. Сопоставление

4.1. Схема сопоставления v1.1.0 MUST быть `closed_blind_rsa`: слепое подписывание RSA.
4.2. Держатель ключа MUST публиковать только открытую часть (`n`, `e`); закрытый показатель
MUST NOT покидать агента.
4.3. Итог сопоставления MUST быть симметричным: обе стороны получают одно и то же
пересечение.
4.4. Офлайн-перебор чужого набора MUST быть невозможен: полученные значения MUST NOT
сопоставляться с догадками без закрытого показателя держателя.
4.5. Число признаков в одном обмене MUST быть ограничено потолком 64. Превышение MUST
отклоняться с кодом `too_many_features`, а не обрезаться.
4.6. Вызов сопоставления MUST объявлять порог: `floor_basis_points` целым числом в диапазоне
0..10000. Вызов без порога MUST быть отклонён с кодом `missing_floor`, порог вне диапазона
MUST быть отклонён с кодом `invalid_floor`.
4.7. Находка ниже объявленного порога MUST NOT возвращаться: результат MUST быть пустым,
конверт MUST нести `floor_basis_points` и `passed_floor`, и полнота MUST называть, что
результат не возвращён как ниже порога.
4.8. Добивка результата до предела MUST NOT применяться.
4.9. Оценка совпадения MUST быть либо вычисленной с объявленным методом, либо
отсутствовать. Константа вместо оценки MUST NOT применяться.
4.10. Число признаков противной стороны MUST NOT раскрываться.
4.11. Документ возможностей MUST публиковать перечень причин отказа сопоставления из семи
кодов: `too_many_features`, `missing_pair_key`, `missing_peer_key`, `missing_private_key`,
`length_mismatch`, `missing_floor`, `invalid_floor`.
4.12. Перед хешированием признак MUST быть приведён к каноническому токену по опубликованному
словарю: строка MUST быть приведена к нижнему регистру и обрезана, а последовательности пробелов,
дефисов и подчёркиваний MUST быть сведены к одному дефису.
4.13. Признак MUST делиться по первому двоеточию на пространство имён и значение; признак без
двоеточия считается значением.
4.14. Пространство имён из списка товаров (`need`, `want`, `offer`, `supply`, `skill`, `service`,
`commodity`, `product`) MUST сводиться к одному значению, чтобы потребность и предложение одного
товара были одним токеном. Любое другое пространство имён MUST сохранять вид `пространство:значение`.
Неизвестное пространство имён MUST считаться свойством: не найти совпадение меньшая ошибка, чем
найти то, чего никто не заявлял.
4.15. Пересечение MUST сравниваться как канонические токены, а каждой стороне MUST сообщаться,
какие из её собственных признаков совпали, в её собственном написании. Реализация, сравнивающая
строки как введены, MUST NOT считаться соответствующей.

## 5. Конверт доказательства

5.1. Каждый вывод и каждый отказ MUST сопровождаться конвертом с полями: `evidence_id`,
`provider`, `operation`, `parameters`, `normalized_result`, `confidence`, `authority`,
`limitations`, `completeness`, `captured_at`.
5.2. `evidence_id` MUST пересчитываться из тела конверта. Дробные числа в теле MUST NOT
применяться: они ломают воспроизводимость. Доли выражаются целыми базисными пунктами.
5.3. Конверт MUST быть подписан ключом агента; подпись MUST лежать рядом с телом так, чтобы
`evidence_id` оставался воспроизводимым, а правка тела ломала проверку.
5.4. `completeness` MUST перечислять, что закрыто, что выброшено и по какой причине.
Отсутствие данных MUST NOT считаться благополучием.
5.5. `confidence` MUST быть из набора: `observed`, `derived`, `claimed`, `unknown`.
5.6. `limitations` MUST называть границы метода прямо, включая то, что схема не закрывает.

## 6. Переговоры

6.1. Переговоры MUST иметь ровно два места и один журнал на пару.
6.2. Действия MUST быть из набора: `propose`, `counter`, `accept`, `decline`.
6.3. Первый ход MUST делать инициатор, и он MUST быть `propose` или `decline`.
6.4. `accept` MUST быть законен только сразу после `propose` противной стороны.
6.5. Предел ходов MUST быть 12. На пределе переговоры MUST оставаться нерешёнными,
отказом они MUST NOT объявляться.
6.6. Отказ MUST нести код из закрытого перечня хода:
`not_a_seat`, `unknown_action`, `already_settled`, `turn_limit`, `not_your_turn`,
`first_turn_is_propose_or_decline`, `seats_must_alternate`, `accept_without_offer`,
`propose_over_offer`, `not_a_witness`, `witness_without_proof`, `witness_card_unverified`,
`witness_seat_mismatch`, `witness_proof_invalid`, `witness_mismatch`.
6.7. Пара MUST NOT открываться, если хотя бы одно намерение неактивно, если оно синтетическое
в сети, объявленной человеческой, если владелец один и тот же, если намерения совпадают, если
стороны из разных сетей или если типы не встречные. Отказ MUST нести код из перечня:
`intent_inactive`, `synthetic_not_admitted`, `same_owner`, `same_intent`, `network_mismatch`,
`types_not_comparable`, `below_required_level`.
6.8. Оба перечня MUST публиковаться машиной в документе возможностей вместе с пределом ходов
и списком действий.
6.9. Документ возможностей MUST публиковать типы намерения, состояния, допустимое
происхождение и перечень причин отказа намерения: `unknown_type`, `unknown_status`,
`unknown_provenance`, `synthetic_not_admitted`, `intent_inactive`, `types_not_comparable`,
`network_mismatch`.
6.10. Сторона MAY записывать ход противной стороны в свой журнал, чтобы оба журнала держали
одну последовательность без общего файла. Это MUST делаться методом `arli/negotiation/witness`.
Свой ход MUST делаться методом `arli/negotiation/turn`; свидетельствовать своё место MUST NOT.
6.11. Запрос свидетеля MUST нести подписанную карточку говорящего и конверт, который говорящий
получил за свой ход. Карточка MUST проверяться по правилам пункта 2, имя в карточке MUST совпадать
со свидетельствуемым местом, конверт MUST проверяться ключом из этой карточки и MUST называть то же
место и действие. Ход MUST NOT быть записан без прошедшего проверку доказательства.
6.12. Свидетельствуемый ход MUST быть законен в собственном журнале принимающей стороны: места
чередуются, предел ходов из пункта 6.5 действует, решённые переговоры не принимают ничего.

## 7. Согласие

7.1. Согласие агента MUST NOT открывать связь. Решение человека MUST быть отдельным действием.
7.2. Молчание, ошибка и тайм-аут MUST NOT считаться ни согласием, ни отказом.
7.3. Одно место MUST NOT решать за другое.
7.4. Повторное решение MUST отклоняться.
7.5. Позднее «да» MUST NOT отменять прежний отказ.

## 8. Хранение и удаление

8.1. Сырые значения признаков MUST NOT храниться на сервере; хранятся отпечатки на время
сессии и конверты.
8.2. Срок хранения конвертов MUST быть объявлен и по умолчанию равен 30 дням.
8.3. Архивация намерения MUST убирать его из сопоставления и помечать связанные конверты
удалёнными.
8.4. Конверты с именами признаков MUST считаться персональными данными и MUST NOT выходить
за регион создания намерения до юридического заключения.
8.5. Документ возможностей MUST публиковать срок хранения, перечень причин отказа хранения
(`unknown_envelope`, `already_deleted`, `unknown_intent`) и утверждение, что сырые значения
признаков на сервере не хранятся.

## 9. Отзыв и ротация ключей

9.1. Смена ключа MUST делать прежнюю карточку недействительной.
9.2. Отзыв личности MUST быть отдельной записью со временем и причиной и MUST NOT
подменяться сменой ключа. Отзыв MUST закрывать заведение новых ключей под тем же
идентификатором до отдельного повторного подтверждения.
9.3. Документ возможностей MUST публиковать причины отзыва ключа (`rotated`, `compromised`,
`principal_request`, `policy`) и перечень причин отказа реестра (`unknown_key`, `key_revoked`,
`key_expired`, `key_not_yet_valid`, `principal_revoked`, `principal_not_confirmed`,
`unknown_revocation_reason`).
9.4. Агент MUST отвечать на `arli/identity/sign` подписью над полученным случаем, над теми же
байтами, что были присланы. Подпись MUST быть ES256 в виде сырой пары R||S, base64url, и ответ MUST
называть ключ, которым подписано. Так сторона, держащая карточку, требует от адреса доказательства,
что по нему отвечает тот же ключ.
9.5. Агент MUST отвечать не чаще одного подписанного случая на адрес и назначение в минуту и MUST
записывать запрос в свой журнал, если спрашивающая сторона себя назвала. Иначе метод становится
подписывающим оракулом.

## 10. Соответствие

10.1. Набор проверок MUST запускаться по адресу реализации:
`python -m arli_engine.conformance --target <url> [--holder <url>]`.
10.2. Набор MUST выдать либо «соответствует», либо точный список расхождений с кодами проверок.
10.3. Набор MUST содержать заведомо неправильные реализации и ловить каждую из них.
Набор, проходящий на любой реализации, MUST считаться недействительным.

## 11. Версии и переход

11.1. Версия расширения MUST следовать семантическому версионированию.
11.2. Несовместимое изменение MUST увеличивать мажорную версию и MUST описываться
в разделе перехода с указанием, что объявляется устаревшим.
11.3. Устаревшее поле MUST объявляться минимум за одну минорную версию до удаления.

## 12. Привязки

12.1. Поверхность агента одна. Привязка (A2A по HTTP, MCP по потокам) MUST NOT добавлять
или скрывать методы: список инструментов MCP MUST совпадать с перечнем методов один к
одному, по одному инструменту на метод.
12.2. Имя инструмента MCP MUST быть именем метода с косой чертой, заменённой на
подчёркивание, и перевод MUST быть обратимым: по имени инструмента MUST восстанавливаться
ровно один метод.
12.3. Причина отказа MUST доходить до вызывающего кодом движка, а не общей ошибкой.
Инструмент, вернувший вместо кода слово «ошибка», нарушает спецификацию.
12.4. Документ возможностей MUST публиковать все привязки, правило соответствия имён и
обязательные поля каждого метода.
12.5. Опись плагина MUST собираться из перечня методов, а не писаться руками, и MUST
объявлять ограничения честно. Записанная опись MUST совпадать с собранной: расхождение
означает ручную правку и MUST считаться дефектом.

## 13. Утверждения о признаках

13.1. Утверждение о признаке MUST нести уровень из закрытого перечня: `declared`,
`third_party_verified`, `topic_owner_verified`. Уровень `declared` означает, что сторона
сказала это о себе, и читать в нём больше MUST NOT.
13.2. Уровень выше `declared` MUST нести выдающего и его собственный конверт. Реализация
MUST проверять конверт выдающего прежде, чем сообщать уровень, и MUST NOT сообщать уровень,
на который конверта у неё нет.
13.3. Утверждение MUST нести момент проверки. Утверждение без него MUST быть отклонено с
кодом `missing_checked_at`. Истекшее или отозванное утверждение MUST сообщаться как истекшее
или отозванное и MUST NOT исчезать молча.
13.4. Отказ по утверждению MUST нести код из закрытого перечня: `unknown_level`,
`unknown_claim_state`, `missing_issuer`, `unknown_issuer`, `issuer_envelope_invalid`,
`claim_expired`, `claim_withdrawn`, `level_upgraded_without_issuer`, `missing_checked_at`.
13.5. Сеть MAY требовать наименьший уровень для пары. Пара ниже этого уровня MUST NOT
открываться, и отказ MUST нести код `below_required_level`.
13.6. Уровень MUST NOT подаваться как подтверждение личности человека за агентом и MUST NOT
считаться переносимым между сетями. Оба запрета MUST быть в документе возможностей.
13.7. Документ возможностей MUST публиковать уровни, состояния, перечень причин отказа по
утверждению и утверждение, что реализация переносит и проверяет чужие утверждения и своих
не выдаёт.

12.6. Отказ по самому вызову MUST нести код из закрытого перечня: `missing_field`,
`unknown_method`, `parse_error`, `bad_type`, `nonce_too_short`, `purpose_required`,
`rate_limited`.
Вызывающий MUST уметь отличить кривой вызов от
сбоя реализации.
